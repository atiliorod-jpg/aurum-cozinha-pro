S1 — P0 CRÍTICO: FECHAR INSERT DIRETO EM `perfis`
================================================================================

Arquivo SQL novo: src/lib/migration10_hardening_perfis.sql
(e menção no README na tabela de migrations)

### Problema confirmado (migration4)
Policy atual (ou equivalente em produção):

  create policy "perfis_ins_v4" on perfis for insert
    with check (id = auth.uid());

Isso NÃO valida restaurante_id nem convite. Um usuário autenticado pode, via
API REST/PostgREST com a anon key + JWT próprio:

  INSERT INTO perfis (id, restaurante_id, nome, cargo)
  VALUES (auth.uid(), '<uuid-vitima>', 'Hacker', 'diretoria');

e entrar na memória do restaurante vítima (quebra multi-tenant).

Onboarding legítimo já usa:
- criar_restaurante (SECURITY DEFINER)
- aceitar_convite (SECURITY DEFINER)

### Correção obrigatória
1) DROP da policy de INSERT em perfis (perfis_ins_v4 e nomes legados).
2) NÃO criar policy de INSERT aberta de volta. Sem policy de INSERT no client
   = só roles/definer inserem (as RPCs existentes).
3) Opcional rede de cinto: policy `with check (false)` se preferir explícito
   (equivalente prático a não ter INSERT).
4) Manter SELECT/UPDATE atuais (perfis_sel_v4, perfis_upd_v4) e o trigger de
   cargo; não afrouxar UPDATE (já impede trocar restaurante_id de forma útil).

### Aceite S1
- [ ] Cadastro “Cadastrar restaurante” ainda funciona (RPC criar_restaurante)
- [ ] Cadastro por convite ainda funciona (RPC aceitar_convite)
- [ ] INSERT manual em perfis com JWT de usuário comum FALHA (403/policy)
- [ ] SQL idempotente + query de checagem no README

Query de checagem sugerida:
```sql
select polname, cmd from pg_policies
  where tablename = 'perfis' and cmd = 'INSERT';
-- Esperado: zero policies de INSERT (ou só uma com check false).
```

S2 — P1: `notas_admin` NÃO PODE VAZAR PARA O CLIENTE
================================================================================

### Problema
Coluna restaurantes.notas_admin (migration9). Policy rest_sel_v4 permite ao
dono do restaurante SELECT da própria linha. O app Admin só usa notas no
super-admin, mas um cliente autenticado pode:

  GET /restaurantes?select=notas_admin

e ler notas internas (VIP, WhatsApp, dívidas…).

### Correção (escolher a mais simples e segura)

**Opção preferida A — tabela separada (mais limpa):**
- Tabela admin_notas (restaurante_id PK/FK, notas text, updated_at)
- RLS: ENABLE; SEM policy para authenticated comum
- SELECT/UPDATE só via RPCs SECURITY DEFINER que checam sou_super_admin()
  (adaptar salvar_notas_admin e o select do Admin)
- Remover ou deixar de usar coluna notas_admin em restaurantes (ou parar de
  selecioná-la; preferir migrar dados se já houver notas)

**Opção B — view / RPC só leitura super-admin:**
- Manter coluna mas NÃO expor via SELECT de restaurantes ao client:
  Postgres não tem column-level RLS fácil → a prática é view sem a coluna
  para o app do cliente, e super-admin lê via RPC
  `notas_admin_do_restaurante(uuid)` com sou_super_admin().
- Client normal: select de restaurantes NUNCA inclui notas_admin no código
  (já é o caso no AuthContext) — insuficiente sozinho; precisa bloquear API.

Implementar A ou B de forma que o teste “select notas como dono” retorne vazio
ou erro.

### Aceite S2
- [ ] Super-admin ainda lê/grava notas no Admin
- [ ] JWT de diretoria do restaurante NÃO obtém o texto das notas
- [ ] Fallback se m10 ainda não rodou: não quebrar Admin (mensagem clara)

S3 — P1: ENFORCEMENT DE BLOQUEIO / PLANO NO BANCO (não só UI)
================================================================================

### Problema
statusAssinatura + BloqueioAssinatura em App.jsx são **só front**.
Com JWT válido e conta bloqueada ou teste/assinatura vencidos, PostgREST ainda
permite insert/update em registros e documentos (RLS atual só checa
restaurante_id, não plano).

Decisão do dono 07/07: corte visual. A reauditoria eleva para P1 se houver
clientes pagantes e risco de bypass técnico.

### Correção obrigatória (mínima e offline-friendly)

Criar helper SQL (SECURITY DEFINER, search_path fixo), ex.:

  restaurante_pode_escrever(rid uuid) returns boolean

Regras alinhadas ao client (utils/assinatura.js):
- se restaurante.bloqueado → false
- se assinatura_ate > now() → true
- senão se created_at + 7 days > now() → true
- senão false
- super-admin em modo suporte: NÃO abrir escrita global; manter regras m7
  (suporte_pode_editar). Ou seja: esta função é para o **tenant dono**, não
  para furar suporte.

Aplicar em policies de INSERT/UPDATE (e se fizer sentido DELETE soft) de:
- registros (exceto talvez auditoria insert-only que já é restrita)
- documentos

Ou trigger BEFORE INSERT OR UPDATE que RAISE se not restaurante_pode_escrever.

**Cuidado offline-first:** o app grava local e sobe depois. Se o plano venceu
durante offline, o outbox pode falhar ao sincronizar — isso é CORRETO
(não gravar na nuvem sem pagar). Não “consertar” fazendo a policy aceitar
sempre. UI já bloqueia; o banco só garante.

**Leitura:** pode continuar permitida (dados históricos) OU também bloquear —
preferência: **leitura OK, escrita bloqueada** (cliente vê que dados existem;
renova e volta). Alinhar com BloqueioAssinatura (hoje não deixa nem ver app —
ok no front; API read-only é aceitável).

- Escrita de suporte continua condicionada a suporte_pode_editar (m7).
