M1 — SEGURANÇA P2: CONVITES TAMBÉM RESPEITAM PLANO/BLOQUEIO
================================================================================

### Problema real (auditoria 17/07 — confirmado no SQL)
Policies de escrita de `registros` e `documentos` usam `restaurante_pode_escrever`
(m10). A tabela `convites` NÃO:

  conv_ins_v4 / conv_del_v4 — só checam meu_restaurante_id + cargo

Efeito: conta **bloqueada** ou com **teste+assinatura vencidos** ainda pode
gerar/revogar convites via API (e possivelmente pela UI se o front não bloquear
100% do Config).

### Correção
Arquivo: src/lib/migration11_convites_plano.sql (novo)

1) Recriar policies de INSERT/DELETE em convites exigindo também
   restaurante_pode_escrever(restaurante_id).

Exemplo de intenção (adaptar nomes e drops legados):
```sql
drop policy if exists "conv_ins_v4" on convites;
drop policy if exists "conv_ins_v11" on convites;
-- manter regras de cargo da m4 (gerência/diretoria; só diretoria convida diretoria)
create policy "conv_ins_v11" on convites for insert
  with check (
    restaurante_id = meu_restaurante_id()
    and restaurante_pode_escrever(restaurante_id)
    and meu_cargo() in ('gerencia','diretoria')
    and (cargo <> 'diretoria' or meu_cargo() = 'diretoria')
  );

drop policy if exists "conv_del_v4" on convites;
drop policy if exists "conv_del_v11" on convites;
create policy "conv_del_v11" on convites for delete
  using (
    restaurante_id = meu_restaurante_id()
    and meu_cargo() in ('gerencia','diretoria')
    and restaurante_pode_escrever(restaurante_id)
  );
-- SELECT de convites pode permanecer sem corte de plano (listar pendentes ok)
```

2) Client (recomendado): em Configuracoes / criarConvite, se a sessão estiver
   bloqueada ou statusAssinatura ok===false, não oferecer gerar convite
   (UX honesta; o banco é a fonte da verdade).

3) README: linha na tabela de migrations + query de checagem:
```sql
select polname, cmd from pg_policies where tablename = 'convites';
```

O2 — OUTBOX: FILA MORTA APÓS N FALHAS
================================================================================

### Problema (auditoria antiga, ainda válido)
`flush` processa a fila item a item. Um item eternamente inválido (payload que
viola constraint / plano vencido permanente / schema) pode ficar preso e o
badge de pendências nunca zera — operador acha que “não sincroniza nada”.

Arquivos prováveis: src/lib/cache.js (outbox*), src/store/AppContext.jsx (flush).

### Correção
1) Em cada item do outbox: `_tentativas` (number), incrementar em falha.
2) Após N falhas (ex.: 8 ou 10): mover para `_outbox_morta` (ou flag `_morto: true`)
   em vez de retentar para sempre.
3) UI Config → Sistema (ou badge):  
   “X pendências · Y com erro permanente” + lista curta (tipo, id, última msg)
   + botão “Tentar de novo” (zera tentativas) e “Descartar” (com confirm, só
   se fizer sentido operacional — preferir não apagar silencioso).
4) reportError (M5) quando item for para a fila morta.
5) Não contar itens mortos no badge “sincronizando” principal (ou contar separado
   em vermelho).

- [ ] UI mostra fila morta de forma honesta
