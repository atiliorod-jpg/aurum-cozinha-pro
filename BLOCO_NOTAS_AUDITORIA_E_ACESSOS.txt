# PARTE 5 — CONVITES / MULTI-USUÁRIO NO MESMO RESTAURANTE
################################################################################

### Como está HOJE (conferido no código)

Limite:
- restaurantes.max_usuarios DEFAULT 3 (migration3 / migration4).
- Client: criarConvite recusa se usuarios.length >= 3.
- Server: aceitar_convite conta perfis ativos e compara com max_usuarios.
- Interpretação: 1 conta dono + até 2 convidados = 3 total.
  (Não é “3 convites além do dono” — é 3 perfis no total.)
- Pagamento.jsx / marketing: “Até 3 usuários com cargos” — alinhado.

Token:
- schema: encode(gen_random_bytes(4),'hex') → 8 caracteres hex (ex.: a1b2c3d4).
- expira_em: now() + 7 days.
- uso único (usado=true após aceitar; FOR UPDATE anti-corrida).
- Cargo no convite: cozinha | gerencia | diretoria (só diretoria convida diretoria).

UI Config → Acessos:
- Gerar convite, copiar código, lista pendentes, revogar.
- Texto: e-mail/senha próprios; código; se cadastra no login.

Isolamento multi-tenant (MESMA memória do restaurante, NÃO de outro):
- INSERT convite: restaurante_id = sessao.restauranteId + RLS
  (só meu restaurante; gerência/diretoria).
- aceitar_convite (SECURITY DEFINER): lê token → pega v_conv.restaurante_id
  → insert perfis (auth.uid(), v_conv.restaurante_id, cargo do convite).
- Dados (registros/documentos) filtrados por restaurante_id via RLS
  (meu_restaurante_id()).
- Conclusão: com migrations 4/5 ok, o código NÃO coloca usuário em outro
  restaurante por acidente — o token carrega o restaurante_id certo.

### Riscos / bugs a verificar e melhorar

R1) ON CONFLICT DO NOTHING no aceitar_convite
    Se o user JÁ tem perfil (já em outro restaurante ou mesmo), o insert do
    perfil é ignorado, mas o convite pode ser marcado usado=true.
    → Pessoa fica no restaurante ANTIGO; convite queimado.
    Correção sugerida: se already has perfil, NÃO marcar usado; raise exception
    'Esta conta já pertence a um restaurante. Use outro e-mail ou peça suporte.'

R2) Conta Auth órfã se aceitar_convite falhar DEPOIS do signUp
    (limite atingido, erro rede). Mitigado em parte por convite_valido antes,
    mas race no limite ainda pode orphanar. Mensagem de erro + suporte limpa
    no Auth admin. Ideal: RPC única “signup_with_invite” (difícil com GoTrue)
    ou documentar limpeza.

R3) Token curto (8 hex) — ~4 bilhões de combinações; rate limit do Supabase
    ajuda. Não expor lista de convites a anon (já fechado). OK para o porte.

R4) Client checa usuarios.length >= 3 mas não conta convites pendentes
    Pode gerar 5 códigos com 1 usuário; só 2 cabem ao aceitar — os extras
    falham no server. Melhor: (ativos + pendentes) < max OU mensagem clara.

R5) Sem mostrar “vagas: 2/3” na UI de Acessos — operador não sabe se cabe.

R6) Sem deep link / WhatsApp share do convite — só “Copiar”.

R7) Demo não testa convite (sessao.demo bloqueia criarConvite).

### O convite é o modelo IDEAL para este app?
SIM, para multi-usuário no MESMO restaurante. Alternativas:

| Modelo | Prós | Contras |
|--------|------|---------|
| Código/token (atual) | Offline-friendly, WhatsApp, sem e-mail obrigatório no convite | Usuário digita errado; token curto |
| Link mágico ?convite= | Menos erro de digitação | Precisa abrir no browser certo / PWA |
| Convidar por e-mail (Supabase invite) | Padrão SaaS | Depende de e-mail; config SMTP |
| PIN da casa (fix) | Fácil na cozinha | Segurança fraca se PIN vaza; todos compartilham identidade |
| 1 login + múltiplos “operadores” locais | Simples | Sem trilha por pessoa; pior auditoria |

RECOMENDAÇÃO: manter código + melhorar UX (link, vagas, mensagem de erro,
WhatsApp share). Não trocar por PIN compartilhado (mata auditoria por pessoa).
